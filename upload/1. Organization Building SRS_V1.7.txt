1 Executive Summary
This document is part of software Requirement specification (SRS), which contain requirements details for the proposed health care software product “iHealthCure”. The objective of this document is to outline the requirements and functionalities of a system designed to manage organizational buildings, floors, and rooms. The system aims to streamline the management process by providing users with tools to add, edit, and view details for each entity (building, floor, room). This system is critical for ensuring accurate and up-to-date information on the infrastructure of an organization.
2 Business Objective & Benefits 
* Efficient management of buildings, floors, and rooms.
* Streamlined workflows for facility managers.
* Improved visibility of infrastructure through searchable and sortable data.
3 Solution Flow
Defining Physical Organizational Structure



4 Functional Requirements
4.1 Organization Building
4.1.1 Building
FR-1Requirements: System should display a page where user will manage Buildings, where following features will available on that page:
1. The system should display a table of buildings with the following columns:
* Building Name: The name of the building.
* Description: A brief description of the building.
* Status: Indicates if the building is active (shown with a checkmark).
* Action: Provides options to view details, and edit information about the building.
2. The system should provide a button labeled "Add Building" that allows users to add a new building to the system. There will be following fields on this page:
* Checkbox: The form shall include a checkbox labeled "Active" that allows users to set the building's status as active or inactive.
* Building Name: The form shall provide a text input field labeled "Building" for entering the building's name. This field is mandatory and must be completed before submission.
* Description: The form shall provide a text input field labeled "Description" for entering additional details about the building. This field is optional.
* Submit: The form shall include a "Submit" button that, when clicked, saves the entered data and adds the new building to the system.
* Cancel: The form shall include a "Cancel" button that, when clicked, discards any entered data and returns the user to the previous page or dashboard.
3. The system should include a search bar that enables users to search for buildings by name or description.
4. The system should allow users to view a specified number of entries per page, with options to navigate between pages.
5. The system should allow sorting of the building list by building name, description, or status.
6. The detail icon should allow the user to view more details about the building.
7. The edit icon should allow the user to edit the building's information.4.1.2 Floors
FR-2Requirements: System should display a page where user will manage Floors, where following features will available on that page:
1. Display a table of floors with columns for:
* Building Name: The name of the building.
* Floor Name: The name of the floor.
* Status: Indicated by a checkmark if active otherwise no.
* Action: Options to view details, and edit.
2. The system should provide a button labeled "Add Floor" that allows users to add a new floor to the system. There will be following fields on this page:
* Status: A checkbox to mark the floor as active. Default state is checked (active).
* Building: A dropdown menu for selecting the building to which the floor belongs. Displays a list of available buildings. User must select one building (required field).
* Floor: A text input field for entering the name of the floor. User must provide a floor name (required field).
* Description: A text input field for entering a description of the floor. Optional field for additional details about the floor.
* Submit: Button to submit the form data. On successful validation, saves the floor details to the database.
* Cancel: Button to cancel the operation. Clears all input fields.
3. The system should include a search bar that enables users to search for floor by name or building name
4. The system should allow users to view a specified number of entries per page, with options to navigate between pages
5. The system should allow sorting of the floor list by floor name, building name, or status
6. The detail icon should allow the user to view more details about the floor.
7. The edit icon should allow the user to edit the floor information.4.1.3 Rooms
FR-3Requirements: System should display a page where user will manage Rooms, where following features will available on that page:
1. Display a table of rooms with columns for:
* Building Name: The name of the building.
* Floor Name: The name of the floor.
* Room Name: The name of the room.
* Status: Indicated by a checkmark if active otherwise no.
* Action: Options to view details, and edit
2. The system should provide a button labeled "Add Room" that allows users to add a new room to the system. There will be following fields on this page:
* Status: Users should be able to mark a room as active or inactive using a checkbox.
* Building: Users must select a building from a dropdown list. The building selection is mandatory.
* Floor: The floor dropdown should populate only after a building is selected.
* Users must select a floor, making this field mandatory.
* Room: Users must enter the room name in a text field. This field is required.
* Description: Users can optionally enter a description of the room.
3. Users can submit the form to save the room details.
4. Users can cancel the operation, which should clear any entered data.
5. The system should include a search bar that enables users to search for room by name, floor name or building name.
6. The system should allow users to view a specified number of entries per page, with options to navigate between pages.
7. The system should allow sorting of the room list by room name, building name, floor name or status.
8. The detail icon should allow the user to view more details about the room.
9. The edit icon should allow the user to edit the room information.

This use case describes how user manage a list of buildings within the system, including adding, viewing, and editing building information.

The system has access to the database where building information is stored.Post conditionsThe building list is updated according to the user's actions. Any changes made to the buildings are saved in the database.PriorityHighPrimary PathActor ActionsSystem Responses1. The user navigates to the building management page.2. The system displays a table with the following columns:
* Building Name
* Description
* Status 
* Action3. The system displays an "Add Building" button at the top of the page.4. The user clicks the "Add Building" button.5. The system displays a form to enter the building's name, description, and status.6. The user fills out the form and submits it.7. The system validates the input and saves the new building to the database.8. The system updates the building list to include the newly added building.9. The user clicks the "View Details" icon in the Action column for a specific building.10. The system displays detailed information about the selected building.11. The user clicks the "Edit" icon in the Action column for a specific building.12. The system displays a form pre-filled with the building's current information.13. The user updates the building information and submits the form.14. The system validates the changes and updates the building information in the database.15. The system updates the building list to reflect the changes.16. The user enters a building name or description into the search bar.17. The system sorts and displays the buildings based on the selected criteria.



18. The system allows the user to choose how many entries to display per page (e.g., 10, 25, 50, and 100) and navigate between pages.Alternate Path Actor ActionsSystem Responses1. The system displays an error message indicating the missing fields.4. The user corrects the form and resubmit.5. The system updates the building list to include the newly added building.6.  The user submits the "Edit Building" form with invalid or incomplete data.7. The system detects invalid input (e.g., missing required fields or incorrect formats).8. The user performs a search that returns no matching buildings.12. The system detects no matching results.13. The system displays a message indicating, "No buildings found matching your search criteria."
